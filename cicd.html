Build your first CI/CD mental model

A lab-style walkthrough that explains what each pipeline stage does, what evidence it should produce, and how a new user can practice it safely.

Pipeline Walkthrough

Think of the pipeline as a sequence of confidence-building checks, not just a button that deploys code.

1

Commit and Pull Request

A change starts with a small branch, clear description, linked work item, and reviewable diff.

  • Practice: write a pull request summary with risk and test notes.
  • Evidence: reviewers can see what changed and why.
2

Static Checks

Linting, formatting, type checks, dependency checks, and secret scanning catch cheap mistakes early.

  • Practice: identify which checks should fail fast before long tests run.
  • Evidence: the pipeline reports clear pass/fail status.
3

Build Artifact

The pipeline creates a repeatable package, often a container image, with a version that can be traced back to the commit.

  • Practice: map an image tag or artifact version back to a source commit.
  • Evidence: the same artifact can move through environments.
4

Automated Tests

Unit, API, integration, browser, accessibility, and performance tests run at the depth appropriate for the change.

  • Practice: decide which tests belong in pull request checks and which belong before release.
  • Evidence: failures explain the broken behavior, not just that something failed.
5

Deploy and Verify

Deployment updates infrastructure or workloads, then smoke tests and health checks confirm the release is usable.

  • Practice: define a three-check smoke test for a web app.
  • Evidence: release logs show what version went where and when.
6

Observe and Roll Back

Dashboards, alerts, and logs reveal whether the release improved or harmed production behavior.

  • Practice: choose one metric, one log query, and one alert that would catch a bad deploy.
  • Evidence: teams can roll back or fix forward using production signals.

Lab Exercises

Use these as discussion prompts or practical assignments for beginners.

Design a Pipeline

  • Pick a simple web app.
  • List the build, test, deploy, and observe stages.
  • Mark which failures should block release.

Debug a Failed Release

  • Read a failed test message.
  • Find the pipeline stage where it appeared.
  • Write the next action for the developer, tester, and operator.
